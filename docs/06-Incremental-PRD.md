# 第一部分 · 增量 PRD（只写变更）

## 1. 变更摘要与产品定位重定义

### 1.1 三条用户决策 → 产品影响

| 用户决策（原话口径） | 对产品的直接影响 | 本文对应章节 |
|---|---|---|
| 性能轻量优先，空闲常驻 **<80MB** 不放宽，接受「Win/mac 各自原生」或 Flutter | 当时把 <80MB 升为验收门槛。**同日后续决定 Windows 用 WPF，这条门槛作废**，见 `docs/10`。轻量仍是体验目标，不是拒发条件 | 6、13 |
| **可砍掉插件生态**，只做内置常用工具 | 产品范围收窄：删除插件运行时、市场、授权、更新、卸载、开发者生态；原 P0 中 2 条砍掉、5 条改写 | 2、3、5 |
| **双端同期可阶段性放宽**，允许一端先行或功能分阶段 | 「同版本号 / 同发布日 / P0-P1 两端 100% 对齐」不再是铁律，改为可执行的分阶段规则 | 4、7 |

### 1.2 新定位与三大约束新状态

> **新价值主张**：一个键呼出，把找应用、找文件、查剪贴板、翻译、算数、截图取色都办完——装好即用，不装插件，常驻不打扰。

| 原约束 | 新状态 | 新定义 |
|---|---|---|
| 通用办公 | **保留，升为唯一主线** | 面向日常办公人群，「少点击、少切换、快速完成一件事」；5 组内置工具开箱即用，不依赖任何安装动作 |
| 开放插件运行时 | **取消**（本次默认） | 不再有第三方插件、插件市场、插件权限模型、插件 SDK / 文档 / 开发者后台；「能力可生长」目标 G2 作废。**是否保留极简内置扩展点列为待确认 Q2** |
| 双端同期 | **改写为「核心对齐 + 增强项分阶段」** | 见第 4 节：核心功能与 4 类结构仍 100% 对齐；同版本号 / 同发布日 / 全量功能对齐放宽 |

> Product Goals 调整：G1（更快完成一件事）**保留并强化**；G2（能力可生长 / 插件）**作废**；G3（双端零迁移成本）**改写**为「核心体验零迁移成本，增强项允许阶段性差异」。

## 4. 双端同期新定义（阶段性放宽的可执行规则）

### 4.1 先行端与理由

> **建议 Windows 先行**（W0 首发），macOS 在 **≤ 8 周**内发布并对齐核心功能。

| 理由 | 依据 |
|---|---|
| 目标用户以国内办公 Windows 为主 | 01-PRD 画像 P1；竞品 Flow Launcher / PowerToys Run / Fluent Search / Rolan / Listary 均为 Windows 原生生态 |
| Windows 侧索引源与权限模型更简单 | Everything / Windows Search / 开始菜单；macOS 需辅助功能、输入监控、屏幕录制、完全磁盘访问逐项授权，未授权会静默失败 |
| 首发风险集中在「一个键办完一件事」的核心链路，先跑通约束少的一端 | 与「核心功能两端必须对齐」不冲突：macOS 版发布时核心功能一次性补齐 |
| 分发与签名成本更低 | Win 侧 winget / 便携 exe / 商店；mac 侧需签名 + 公证 |

### 4.2 分阶段规则（不允许「看情况」）

| 类别 | 是否允许分阶段 | 最长间隔 | 具体范围 |
|---|---|---|---|
| **核心功能** | ❌ **不允许** | macOS 发布日即 100% 对齐 | 全局呼出 / 隐藏、模糊 + 拼音搜索、应用 / 文件 / 网址启动、分组与拖拽、5 组内置工具、失焦隐藏 / 多屏、首次引导 |
| **4 类结构** | ❌ **不允许** | 任何时刻 100% 对齐 | 数据 schema、快捷键语义、视觉规范（5.7 尺寸 / 5.8 配色 token）、设置项结构 |
| **平台特有系统能力深度适配** | ✅ 允许 | macOS 首发后 **≤ 8 周** | macOS 辅助功能 / 屏幕录制 / 完全磁盘访问流程、Windows Everything 索引桥、高 DPI / 多屏边缘场景 |
| **V1 增强项** | ✅ 允许 | Windows 首发后 **≤ 16 周** | 选区上下文 / 超级面板（内置工具版）、`⌘K` 操作菜单、云同步、深色主题、快捷键别名、本地化文案细节 |

### 4.3 仍必须对齐（任何差异视为缺陷）

数据 schema（分组 / 快捷项 / 剪贴板 / 设置的结构与字段）、快捷键语义（`Alt`↔`⌥`、`Ctrl`↔`⌘` 映射与行为一致）、视觉规范（浮层尺寸、圆角、间距、配色 token、字体层级）、设置项结构（Tab 数量、条目、默认值语义）。原 `01-PRD.md` 第 6.6 节 **13 项平台差异白名单继续有效**，并新增「阶段性差异清单」作为唯一合法的临时差异来源。

### 4.4 发布节奏与版本号

| 节点 | 时间 | Windows | macOS | 版本号规则 |
|---|---|---|---|---|
| MVP | W0 | ✅ 首发 | — | 允许 `0.9.x-win` 平台后缀 |

> 补充：微软正把 PowerToys 17 个工具从 WPF 迁 **WinUI 3**（减体积、统一 Win11 视觉），但 **Run 为保 22+ 插件不迁** [S18]；Raycast 官方亦以「微软 UI 框架历史混乱（WPF→UWP→WinUI 3 仍年轻）」否决 Windows 纯原生双 UI 路线 [S01]。

### 11.2 为什么两边不同

| 维度 | Windows | macOS | 对产品的含义 |
|---|---|---|---|
| 系统 API | Win32 / COM、开始菜单与 UWP 应用清单、`RegisterHotKey`、托盘 Shell_NotifyIcon | AppKit / LaunchServices、Accessibility（辅助功能）、Input Monitoring、Screen Recording（截图）、Full Disk Access（文件搜索）、`NSStatusItem` 菜单栏 | 全局热键、菜单栏 / 托盘、截图取色、文件索引**两端都要分别原生实现** |
| 索引源 | Everything（MFT）/ Windows Search / 开始菜单快捷方式 | Spotlight 元数据 / LaunchServices / `/Applications` | Raycast 2.0 自研 Rust 索引器在 Win 直读 MFT，正是为绕开两端索引差异 [S01][S03] |
| 权限模型 | 开机自启 / 管理员权限 / SmartScreen 签名 | 逐项用户授权，**未授权会静默失败**（Whisk 剪贴板管理器也因 macOS 剪贴板读取权限需专门引导 [S25 类比]） | 首次引导 Step3 必须按平台列权限，且「未授权给明确引导」是硬要求 |
| 分发渠道 | winget / scoop / choco / Microsoft Store / 绿色便携 exe | DMG / Mac App Store + **签名与公证** / Homebrew cask | 签名公证成本与首发节奏不同，是「Windows 先行」的实务理由 |
| UI 框架成熟度 | 微软 UI 框架反复（WPF→UWP→WinUI 3），且 WPF 与插件生态强绑定 | AppKit 稳定；SwiftUI 在键盘优先 / 高性能列表场景被弃用 | 同一套 UI 代码在两端跑，需要「系统 WebView + 原生壳」或「各端原生」，二者代价不同 |

## 12. Flutter Desktop 专项（写实，不为迎合而美化）

### 12.1 生产案例核实结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **发现过 1 个生产案例：Wox v2 早期 UI 层曾用 Flutter**（第三方称「Tauri + React/Flutter」，版本演进文章记录 v2.4.0-beta.2 为分水岭） | [S21][S22] |
| 2 | **但已被主动弃用**：v2.4.0（2026-07~08）「用嵌入式原生 UI 替换 Flutter UI」，**去掉独立 Flutter 进程**，进程内管理窗口 / 焦点 / 控件 / GPU 渲染；官方 changelog 口径「**日常内存大约减半到约 150MB**」 | [S21] |
| 3 | 当前（2026-11）Wox 官方 README 明确「**fully native GPU rendering，not Electron、not a browser shell**」，仓库语言 Go 86.91% + Objective-C 2.19%，**未发现仍在维护的 Flutter 桌面启动器生产案例** | [S20][S23] |
| 4 | **第三方口径冲突**：iplaysoft / mygit 称 Wox v2 为「Go + Tauri + React/Flutter」，与官方 README「not a browser shell」矛盾，且 [S21] 说明 Flutter 已移除 → **以官方 README + changelog 为准，第三方说法未核实 / 已过时** | [S20][S21][S22] |
| 5 | **Raycast 官方第一手**：评估过「Flutter、Qt、React Native for Desktop、Swift 跨平台」，「**ruled them out very early**」，理由为「lacked the native control we needed」或「not mature enough for our user base」 | [S01] |
| 6 | Flutter 桌面**其他品类**有生产案例（FlClash 代理客户端、AppFlowy 文档工具），但均需大量原生代码或 Rust 后端，**不是轻量启动器品类** | [S25][S28] |

> **给用户的直白结论**：桌面启动器品类里「用过 Flutter 的那一家，已经为了把内存砍一半而把 Flutter 换掉了」；这个品类当前没有正在维护的 Flutter 生产案例。用户是 RN/Flutter 背景，但本品类最脆弱的三件事恰好是「常驻 + 全局热键 + 托盘/菜单栏」。

### 12.2 系统能力适配成本（逐项写实）

| 系统能力 | Flutter 现状 | 适配成本 / 风险 | 来源 |
|---|---|---|---|
| **全局热键** | 靠 `hotkey_manager` / `global_shortcuts` 插件；快捷键多为应用内 `Shortcuts`/`Actions` | Windows 可行；**Linux Wayland 因安全模型不允许全局键盘监听直接失效**；有实测案例 `hotkey_manager_linux` 调用 `keybinder_bind` 失败却仍上报成功 → **热键静默失效、无异常可捕获** | [S26][S27][S30] |
| **系统托盘 / 菜单栏 / 原生菜单 / 右键菜单** | `tray_manager` / `system_tray`、`PlatformMenuBar`（3.7+）、`ContextMenuController` | 实测：GNOME 46 下托盘图标**第二次点击菜单不弹出**、插件层无法修；各端菜单语义需分别适配，且勿与系统快捷键冲突 | [S26][S30] |
| **无焦点悬浮面板 / 窗口显隐** | `window_manager` / `desktop_multi_window` | 实测：隐藏后复现的窗口带**过期冻结帧 / 花屏**，与合成器 show/hide 时序相关，属结构性问题 | [S26] |
| **文件索引** | 无内置能力 | 需 FFI / 平台通道调用原生（Win32 / MFT / Spotlight）或外挂 Rust 后端；Raycast 自研 Rust 索引器、Wox v2 加 NTFS 快速索引均为独立重活 | [S01][S21][S28] |
| **文件拖放 / 打包 / 签名 / 公证** | **Flutter 本身不提供原生拖放**，需 `desktop_drop`；打包为 MSIX / DMG+公证 / AppImage 三套 | 本产品 P0-14「从系统拖入添加快捷项」是核心交互，属必须额外验证项；mac 公证为分发必需，三套构建签名流程 | [S27][S30] |
| **内存基线** | 独立 Flutter 引擎 + Dart VM；Wox v2 去掉独立 Flutter 进程后内存减半 | **与 <80MB 硬约束直接冲突**，需实测证据证明可压到阈值内；本品类尚未见该证据 | [S21] |

> **两条最有力的反面证据**：Wox v2 官方 changelog 显示「内存减半后仍约 150MB」，**仍高于本次 80MB 门槛** [S21]；[S26] 的 Linux 截图工具因托盘二次点击失效 / 热键静默失败 / 隐藏窗口花屏，最终重写为「C++ 常驻 daemon + Flutter 按需 UI」双进程，Flutter 不再承担常驻与系统能力。本文**不据此下选型结论**，只把事实与成本交给架构师（任务 #8）。
